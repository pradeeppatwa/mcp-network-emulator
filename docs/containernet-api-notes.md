**Containernet API — Week 3 Notes**

Containernet is a fork of Mininet, not separate software — it inherits everything (addSwitch, addLink, addController, the CLI) and adds one genuinely new capability: Docker-backed hosts via `addDocker()`.

A core distinction confirmed by reading and tracing `containernet_example.py`: every `addHost`/`addSwitch`/`addLink` call before `net.start()` only builds an in-memory description of the topology — nothing exists on the real OS (no namespace, no container, no OVS flow) until `net.start()` actually runs. This matters because it means topology-building and live-modification are fundamentally different kinds of operations against this API.

`addDocker()` accepts resource-limiting parameters (`cpu_period`, `cpu_quota`, `cpu_shares`, `cpuset_cpus`), networking parameters (`ip`, `ports`, `port_bindings`), and storage (`volumes`). Verified `cpu_period=50000, cpu_quota=25000` is a real, OS-enforced limit, not just an accepted argument — confirmed via `cat /sys/fs/cgroup/cpu.max` inside the running container, which printed `25000 50000` matching the Python call exactly.

**Most important finding this week:** `addLink(cls=TCLink, delay=...)` only sets delay/bandwidth/loss at link *creation* time. The real `set_delay`/`set_bandwidth`/`set_loss` tools need to modify an *already-running* link instead. The mechanism is `node.connectionsTo(otherNode)` to locate the interface pair, then `.config(delay=...)` directly on one interface. Verified by hand: added 200ms to one direction of an already-running `s1<->s2` link (which already had 100ms from creation) and watched ping RTT shift from ~200ms to ~301ms — confirms the change was one-directional (only one interface reconfigured), not the full 100+200=300ms-each-way that reconfiguring both sides would have produced.

`node.cmd()` runs an arbitrary shell command inside a node's namespace and returns its text output — this is the general mechanism `get_routing_table()` will use (`node.cmd('ip route')`), since there's no dedicated Mininet API for routing tables. Finding worth flagging: every container's routing table includes a Docker bridge-network route (`172.17.0.0/16`) alongside the actual emulated-topology route — a real implementation needs to filter or label these separately, or the AI/user gets a confusing mixed answer.

`net.pingFull()` returns a list of tuples, one per direction, each holding `(src_node, dst_node, (sent, received, rtt_min, rtt_avg, rtt_max, rtt_mdev))` — this is the literal shape `ping()` will need to parse. `net.iperf()` failed in testing with "Could not find telnet" (base Ubuntu image lacks iperf/telnet by default) — and this failure cascaded into a broken `net.stop()` on exit, a concrete lesson that one tool's failure can corrupt unrelated later state if not handled carefully.

**Topo subclass vs. flat scripting, for `create_topology(config)`:** Topo subclassing earns its value through *reuse* of one shape with different parameters (e.g. `SingleSwitchTopo(n=2)` vs `(n=10)`). `create_topology(config)` receives a fresh, one-off config per AI call with no reuse case — so flat scripting (loop directly over config, call `addHost`/`addLink`) is the better fit here, with one less layer of indirection. This could be revisited if a future feature allowed saving/reusing named topology presets.

**Open item for Week 9:** Containernet ships `examples/faultinjector_examples/` with files like `link_degradation_example.py` and `random_link_example.py` — closely matching the planned `set_delay`/`set_loss` tools. Worth investigating before implementing these from scratch, in case Containernet already provides a tested mechanism to build on rather than reimplement.
